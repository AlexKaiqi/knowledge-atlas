# 探索与环境资产维护

决策日期：2026-09-08。建议以 Docker/OCI 作为需要系统环境时的主要运行方式，以 Dev Containers 提供可选开发入口，需要多个服务时再加 Compose。这是结合官方工具边界做出的项目选择，不是学习效果研究结论。

长期资产是一份能重新建立环境、继续探索、检查已有结果的工作包。运行中的容器是其中一个实例；退出或重建实例不应丢掉有价值的东西。

## 资产分开放，但能互相找到

| 资产 | 保存方式 | 怎样维护 |
| --- | --- | --- |
| 问题、假设、代码与小型输入 | `explorations/<主题>/`，Git | 自由正文；留下来源、运行入口和继续方向 |
| 环境定义 | `environments/<环境名>/`，Git | Dockerfile/镜像引用、实际依赖锁、说明；按需要加 Dev Container 或 Compose |
| 已构建镜像 | 本地缓存或镜像仓库 | 重要运行记录 digest、平台；需要长期存档时保留镜像副本及校验值，巨大 tar 不进 Git |
| 持续工作数据 | 明确的本地目录、命名卷或外部存储 | 记录归属、位置、备份和恢复办法；每段探索独立写入区 |
| 一次运行的证据 | 探索下 `runs/<运行名>/` 或外部存储引用 | 保存值得引用的输入版本、命令、输出、解释；重跑新增记录 |
| 可复用解释 | `knowledge/<条目>/` 或现有服务修订 | 引用具体探索/运行和来源，保留条件与未知 |

目录名字可以调整；一份 README 足以起步，没需要不创建空的元数据、目录或数据库。共享的内容放 Git，私人/临时内容放 `.local/` 或仓库外。Git 中留足以定位外部大文件的版本、校验值、权限归属和取得方法；有实际规模再选 Git LFS、DVC 或对象存储，不先建资产平台。

## 什么才算一次可复查运行

用自然语言记清：回答的问题；代码提交或实际文件摘要（有未提交修改时保存相关差异）；所用环境定义和实际镜像 ID/digest、CPU 架构；输入来源、参数和随机种子（如适用）；运行命令、退出状态、关键日志与输出；观察、解释和下一步。

小文件可以直接保存；大文件保留不可混淆的版本引用和校验值。只写“latest”“运行成功”或贴一张图不足以继续验证。镜像固定也不保证不同架构、GPU 驱动和外部服务产生逐位一致结果，应说明接受的误差或已知差异。

运行记录是可读的证据，不要求所有人填写同一表格。Agent 负责整理已有事实，不能补造缺失日志或把计算模型的输出写成真实世界观测。

## 环境复用与演进

按依赖和用途复用少量环境定义，不给每篇知识复制一个 Dockerfile。同一环境可以服务多段探索，每段探索使用独立实例和写入区；有不同依赖时再派生环境，说明从哪里分出。

基础镜像用可读 tag 加 digest；依赖使用对应生态的锁定方式。tag 会变化，固定 digest 可标明所用版本，但也需要主动评估更新，不能指望旧摘要自动获得修复。修改环境后重跑代表性用例，保留旧运行的引用，不把历史结果改成新环境版本。[Docker 构建建议](https://docs.docker.com/build/building/best-practices/)

重要里程碑需要同时考虑“能重新构建”和“能取得当时镜像”：外部包或镜像可能消失，必要时在有权使用的存储中保留副本。容器里临时安装成功的依赖要回写环境定义；`docker commit` 可作临时救援，但不包含挂载卷内容，不能替代源码、依赖和数据归档。[Docker commit 边界](https://docs.docker.com/reference/cli/docker/container/commit/)

## 数据持久化与恢复

代码、输入和结果需要被人和 Agent 直接查看时，优先 bind mount 明确的目录。数据库内部数据适合独立命名卷；卷在容器删除后仍可存在，但不会随 clone 自动复制，也没有因此获得备份。[Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/) · [Volumes 与备份](https://docs.docker.com/engine/storage/volumes/)

每个有状态环境在自己的说明中记录：谁的卷/目录、怎样停止写入或一致性导出、备份在哪里、怎样恢复到一个新实例、上次恢复验证何时完成。数据库优先使用自身的一致性备份方法；不能直接压缩正在写入的目录就宣称备份可靠。旧备份保留到新实例读取和代表性操作都验证完成。

日常可停止和重建运行实例；缓存可按需清理。清理命名卷、唯一镜像副本或原始数据前先明确归属及可恢复副本。不使用全局 `docker system prune --volumes` 作为本项目的日常维护命令。`.local/` 虽被 Git 忽略，也可能有用户唯一的数据，不能当作随时可删的缓存。

## 工具如何选择

| 场景 | 项目建议 |
| --- | --- |
| 只有简单 Python 依赖 | venv + 依赖锁即可，`.venv` 从定义重建 |
| Linux 系统库、多语言工具链或稳定演示 | Docker/OCI |
| 同时依赖数据库、应用等多个服务 | Compose，按探索区分项目和数据卷 |
| 希望编辑器或兼容工具进入同一环境 | 在 Dockerfile/Compose 上加 Dev Container |
| 已有 Nix 经验，需要可声明的多语言开发环境 | 可选 Nix，固定相关依赖版本 |
| 研究完整 OS、内核模块或整机行为 | VM，必要时专用机器 |

Dev Containers 补充已有镜像、Dockerfile 和 Compose，不需要再定义一份依赖；初始化应可重复执行，不清空已有数据。它是开发入口，不自动等同于敌对代码沙箱。[Dev Containers 规范](https://containers.dev/) · [Python venv](https://docs.python.org/3/library/venv.html) · [Nix 开发环境](https://nix.dev/tutorials/first-steps/declarative-shell.html)

可信开发时可以挂载自己的探索目录；对来源不明的代码只开放必要输入和独立输出，限制资源与网络。不要默认把整个宿主目录、Docker socket、模型凭据和生产数据库挂进实验。多用户云执行如有需求，应选择已有专用隔离服务，不在本仓库建设全套云 Agent 沙箱。

## 当前落地与范围

仓库提供 [Python 标准库环境](../environments/python-stdlib/README.md)，包含固定镜像定义、可选 Dev Container 和不用安装 Agent 的运行示例。它验证环境入口和文件保存，不宣称任何知识主张已被实验确认。

现有网页的 `server/docker-runner.mjs` 是短时、受限的 Python 执行适配；输入和小型结果进 SQL。它不保存完整可继续开发的工作目录，也不会自动登记到资产树。网页结果需要明确导出整理，才能成为仓库资产。自定义环境通过下述文件资产与已有 Agent 构建，不扩建通用网页 runner、调度器或镜像仓库服务。


## 在网页创建与共建环境

实践页的「新建环境」允许先描述用途，再从 Python 或空白起点建立私人环境。Python 起点来自已维护的基础 Dockerfile，加上明确标为示例的 run.py；描述用途不代表已经自动实现这个实验。参与者可自行编辑任意安全路径的文本文件，也可让已有 Agent 补齐后导入。文件格式自由，Dockerfile、Compose、依赖锁文件和验证说明按需要提供。

环境作为独立 SQL 资产维护，不依附整个探索的分享范围。创建者明确分享当前版本；别人阅读后加入共建，按基础版本提交共同修改，或派生一份自己的私人环境。历史私人版本不会随分享公开；如果旧探索引用了尚未公开的版本，可先分享当前环境，再在版本记录中明确分享那个历史版本。其余私人历史仍不公开。撤回后他人不能继续读取或编辑原环境。派生关系只在来源仍有权访问时展示，已复制的内容不会被来源撤回。

「带到探索」复制所选版本、文件和用途为固定成果快照，后续修订不改变旧实验。私人版本只能进入私人探索；探索之后要共享，必须先明确分享快照引用的那个环境版本。原来已明确共享的副本仍可保留。多人编辑与分享都由服务判断身份和版本，前端不能授予维护角色。

「交给自己的 Agent」只导出选定环境，不附私人探索或历史。环境包为 `knowledge-atlas/environment-1`，含自由 `purpose`、`files: [{path, content}]` 及 `source: {id, version}`；这一小段协议用于往返身份与版本，不约束正文结构。文件总内容最多 28,000 UTF-8 字节、最多 20 个文件；HTTP 提交最多 48 KB，数据、镜像和完整日志另存并在说明中留下位置。

导入只预览文本，不执行配置。Agent 将包落到全新专用目录，先检查 Dockerfile、Compose、Dev Container 和脚本，再使用原生工具。构建上下文限定所需文件，不把宿主目录、Docker socket 或账号凭据加入包；`initializeCommand` 可在宿主运行，不能把 Dev Container 配置视为纯静态资料。独立包的命令以包根目录为基准，不能继续假设整个知图仓库都在场。[Docker 构建上下文](https://docs.docker.com/build/concepts/context/)、[Dev Container 属性](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainerjson-reference.md)

实际构建与运行后，保留源 ID/版本返回环境包，在原环境「编辑与导入」中审阅并保存新版本。若其他人已有修改，比较最新内容后合并；不直接覆盖。自由验证说明应区分谁实际运行、运行条件/命令、结果、限制；参与者上传日志不是平台自动验证。镜像构建成功、容器运行成功和实验结论成立分别记录。完整运行记录与数据保留独立位置。[镜像](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)、[卷的生命周期](https://docs.docker.com/engine/storage/volumes/)

Git 的 environments/ 与网页 SQL 各有权威来源；环境包是工作副本，没有自动同步、自动执行、自动发布或后台构建服务。


## 浏览器工作目录

本地 Codex 工作面板使用的 AIO 实例与 SQL 环境定义分别维护。应用文件在 `.local/workspaces/<数据库命名空间>/<探索 ID>/workspace/`，容器暂停后仍保留；浏览器会话和后台进程不等于备份。来源、镜像摘要、启动与恢复边界见 [浏览器接入](BROWSER_WORKSPACE.md) 和[环境入口](../environments/browser-workspace/README.md)。从这些文件选择有价值的版本，经过已有成果/环境包流程沉淀，不自动公开整个目录。
