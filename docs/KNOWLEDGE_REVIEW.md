# Agent 维护的知识审阅规范

这是一份质量责任说明，不是排版模板。原则来自 [学习方法调研](LEARNING_METHODS.md)，方法与检查参考统一维护在 `content/learning/methods.json`。用户不用手动填满规范；维护 Agent 应替用户整理、提出缺口与可复核修改。

## 什么叫相对完整

在明确范围内能独立理解、可追溯，并知道怎样继续检验：

1. 回答什么问题，或说明什么对象？
2. 当前解释、方法或主张是什么？
3. 根据什么这样说？原始文献、证明、原始材料、数据与可复现实验都可以成为依据。
4. 哪些条件、未知、反例或分歧会改变答案？
5. 想深入时，应补什么背景、检查什么证据或做什么尝试？

这五项是内容责任，不要求五个同名标题，也不要求每项单独储存。定义、定理、使用方法、争议综述和原创观察承担不同责任。尚未完整的内容可以作为明确标注的草稿共享。

## 方法怎样检查

每次新增或实质修改知识，维护者阅读方法清单，对相关条目说明：适用性及理由；满足 / 需改进 / 不适用；证据与待办。可以用自然语言写一段审阅，不强制复杂 schema。方法版本、实际审阅者和时间可查询即可。

- 解释抽象、读者缺少背景时，考虑支架、例子、直接讲解和按需深入。
- 需要诊断误解时，考虑预测或对比；无需让所有读者先答题才能看解释。
- 需要保持记忆时，考虑检索与间隔；没有统一最优时间表。
- 需要应用时，考虑换条件、迁移和实际操作；只读词条不一定需要完整练习。
- 使用模拟或生成工具时，检查模型假设、变量、观察目标与结果来源。
- 争议知识保留竞争解释和证据边界；不以总结共识的口吻掩盖分歧。

程序仅强制稳定标识、合法版本、已提供的引用、可执行协议、权限和数据大小。提供选择题时需要合法答案与对应反馈；没有选择题的正文同样合法。不再强制中英文双标题、三层讲解、工程含义、五种教学方法或第二份配套 JSON。

## Agent 如何维护

使用者选择的 Agent 通过项目 Skill 维护资料，不依赖本站后台 Agent。Git 中可从探索记录和选定运行提炼知识；服务中可从选定成果版本创建私人草稿。自由完善后按用户明确选择的范围共享或纳入维护。可以共享未完成草稿，不等于确认主张。

普通措辞整理可以按项目策略自动合并；涉及结论、证据、权限或有争议内容的变更须有相应依据，无法解决的分歧进入待办。并非所有修改都等待真人许可。实际人审和真人试学必须有真实记录，Agent 不能替它们签名。

每次变更记录基础版本、差异、理由、作者、来源和可能受影响的关系。遇到并发修改要合并，不覆盖。关系理由要说明为何有助于引导；“相关”不能自动当作“支持”。正文的来源与知识之间的关系分别维护。

当前网页里的审阅文字属于提交者的编辑自查，不能宣称已经独立审稿。外部 Agent 接入见 [使用自己的 Agent](AGENT_USAGE.md)，知识与服务归属见 [探索与协作设计](EXPLORATION_SERVICE.md)。

## 自由正文与旧内容适配

Clone 后新增 Git 自有知识可在 `knowledge/` 维护自由 Markdown，探索过程留在 `explorations/`。知识引用实际依据、相关条目及具体运行版本，Git 保留修订；这些目录尚未自动进入网页索引。

服务内可用“沉淀为知识草稿”，正文由 SQL 保存修订。既有 `content/knowledge/*.json` 是种子适配层，旧发布命令继续可用。导出工具把服务记录还原为目录，建议放 `.local/exports/` 或仓库外；导出副本不是数据库的第二写入源。整理为 Git 自有条目需保留来源、对应版本和派生关系。

`npm run check` 检查已有内容、服务数据约束和构建。结构通过不代表事实正确或教学有效。静态预写导学是一个可选表现形式；自由问题可以直接进入探索工作区。

## 真人试学记录（仅适用时）

记录单元与版本、学习者背景、独立任务、错误解释与卡点、给过的提示、换情境表现和延后回忆。明确没做的部分。需要验证的是是否更能解释、判断或完成目标任务，不能用阅读完成代替。
